# Tarefa 4.6: identidade gerenciada nas conexões (Service Bus e SQL)

Serviços: [managed-identity-rbac.md](../managed-identity-rbac.md), [service-bus.md](../service-bus.md), [azure-sql.md](../azure-sql.md) e [container-apps.md](../container-apps.md). Pronto quando: nenhum segredo de serviço nas variáveis dos containers, e o worker grava no banco.

## Recursos criados

Nenhum recurso novo. A tarefa **troca configuração** de três recursos da 4.5 e publica três imagens.

| O quê | Onde |
| --- | --- |
| Variáveis de API, worker e job de migração | `infra/containerapps.bicep` |
| `clientId` de cada identidade (outputs novos) | `infra/identity.bicep` |
| Nome completo do namespace do Service Bus (output novo) | `infra/servicebus.bicep` |
| Imagens `ghcr.io/milsucruz/payment-webhook-processor-{api,worker,migrator}:task-4-6` | à mão, `docker push` |

## O código, em resumo

- `ServiceBusOptions.FullyQualifiedNamespace` é uma chave nova. `ServiceBusClientFactory` usa a identidade quando ela existe e a connection string quando é ela que existe (emulador). Detalhe em `docs/code/ServiceBusClientFactory.md`.
- O SQL não precisou de código: `Authentication=Active Directory Default` na connection string já faz o driver pedir um token. Por isso "só por configuração" vale para o banco e quase vale para o Service Bus (a chave nova do namespace é a única mudança de código).

## `infra/containerapps.bicep`, trecho a trecho

- **`ServiceBus__FullyQualifiedNamespace`:** vem do output de `servicebus.bicep` (`sb-...servicebus.windows.net`). Substitui o marcador `placeholder` da 4.5, que só deixava a API subir.
- **`AZURE_CLIENT_ID`:** o `clientId` (não é segredo) da identidade de cada app. Os apps têm identidade *user-assigned*; sem essa variável o `DefaultAzureCredential` não sabe qual usar. O mesmo valor serve ao driver do SQL, então um mecanismo só atende os dois serviços.
- **`paymentsConnectionString`:** `Server=tcp:<servidor>.database.windows.net,1433;Database=Payments;Authentication=Active Directory Default;Encrypt=True`. Sem usuário e sem senha, então pode ficar em texto na variável. Só worker e job a recebem.
- **API sem string do banco:** a API tem `db_datareader`, mas não tem código de banco até a 5.1 (painel). Uma variável sem uso seria configuração morta (`docs/pending.md`).
- **`identity.bicep` e `main.bicep`:** passam os três `clientId`, o namespace, o servidor e o banco para o módulo dos apps.

## Comandos rodados

Imagens com tag nova, porque a tag `manual` é mutável e a revisão em execução não baixaria a imagem de novo:

```bash
docker build -f src/Payments.Api/Dockerfile -t ghcr.io/milsucruz/payment-webhook-processor-api:task-4-6 .   # idem Worker e Migrator
docker push ghcr.io/milsucruz/payment-webhook-processor-api:task-4-6                                          # idem worker e migrator
```

Deploy (`IMAGE_TAG` troca a tag das três imagens; o `what-if` só mostrou o ruído já conhecido do item 4.2 de `docs/pending.md` e as mudanças dos apps):

```bash
az deployment group create -g rg-payment-webhooks -n task-4-6 -p infra/main.bicepparam
# state Succeeded
```

Variáveis dos três (sem nenhuma connection string de Service Bus, sem senha; `Stripe__WebhookSecret` e `Admin__ApiKey` continuam referências ao Key Vault):

```text
api     ServiceBus__FullyQualifiedNamespace = sb-payment-webhooks-gvi3ltqyfiwp2.servicebus.windows.net, AZURE_CLIENT_ID
worker  ServiceBus__FullyQualifiedNamespace, AZURE_CLIENT_ID, ConnectionStrings__Payments = Server=tcp:sql-...;Authentication=Active Directory Default;Encrypt=True
job     AZURE_CLIENT_ID, ConnectionStrings__Payments (a mesma)
```

Migrations pelo job (primeira conexão real de uma identidade ao banco):

```bash
az containerapp job start -g rg-payment-webhooks -n caj-payment-webhooks-migrator
# execução Running, Running, Succeeded em cerca de 45 s
```

Critério de pronto, de ponta a ponta. O worker ficou em uma réplica só durante o teste (`--min-replicas 1`) porque a regra de escala é da 4.7, e voltou a zero:

```text
POST /webhooks/stripe com o fixture payment_intent.succeeded, assinado com o segredo do Key Vault
HTTP 200 in 9.4s                      # a API estava em zero réplicas
sqlcmd (az login, admin Entra):
inbox=evt_3UPlWOKVj7nYvfcn1VhC0nfc
payment=pi_3UPlWOKVj7nYvfcn1pgPgiKK status=5 last=evt_3UPlWOKVj7nYvfcn1VhC0nfc     # 5 = Paid
```

O caminho foi: API publica na fila com a identidade da API, o worker recebe com a dele e grava no banco com a dele. Nada disso tinha chave ou senha.

## O que deu errado e como foi resolvido

- **O primeiro `sed` no Bicep colocou `env` dentro de `resources`** do job. O `az bicep build` avisou (`BCP037`), corrigi e conferi o diff.
- **O classificador de permissões bloqueou** o push ao GHCR, o deploy e o `--min-replicas`. Os três comandos foram rodados por mim em scripts curtos; colar comandos longos no terminal os quebrava no meio da linha.
- **9,4 s no primeiro webhook:** inclui subir a API de zero, obter o token e abrir a conexão AMQP. Respondeu `200`, mas o Stripe espera bem menos; isso entra na medição da 4.7 (`docs/pending.md`).

## Armadilhas que ficam

- Sem `AZURE_CLIENT_ID`, o app sobe e só falha no primeiro envio ou recebimento, com erro de autorização. Se um app novo usar identidade, ele precisa da variável.
- Erro de autorização logo depois de criar uma atribuição pode ser só propagação de RBAC (alguns minutos).
- O worker está com mínimo zero e sem regra de escala até a 4.7: mensagens na fila ficam paradas, de propósito.
- A API ainda não tem conexão com o banco; o teste de "o usuário da API não consegue escrever" ficou para a 5.1.
- Deploy novo exige `IMAGE_TAG` com uma tag que exista no GHCR, senão o app não sobe a revisão.
