## O código, em resumo

- **`infra/main.bicep` e `containerapps.bicep`:** `apiImageTag`, `workerImageTag` e `migratorImageTag` no lugar de `imageTag`. Três, e não dois, porque se o pipeline falhar entre a troca da API e a do worker, cada um fica numa tag e o próximo deploy deve manter a de cada um.
- **`infra/main.bicepparam`:** lê `API_IMAGE_TAG`, `WORKER_IMAGE_TAG` e `MIGRATOR_IMAGE_TAG` **sem padrão**. Antes o padrão era `manual`, e um deploy manual sem a variável voltaria os três apps para a imagem da 4.5 sem avisar. Agora falha:

  ```text
  Error BCP427: Environment variable "API_IMAGE_TAG" does not exist and there's no default value set.
  ```

- **`src/Payments.Migrator/Program.cs`:** `EnableRetryOnFailure()` no `UseSqlServer` (pendência 2.3). A 3.1 recusou essa estratégia no worker porque ele tem atrasos próprios e transações abertas pelo código; o migrator não tem nenhum dos dois, e o `MigrateAsync` roda dentro da estratégia. O padrão do EF são 6 tentativas com atraso exponencial até 30 s, e o 40613 ("database is not currently available") do banco pausado está na lista de erros transitórios do EF.
- **`.github/workflows/ci.yml`:** passo `Bicep build` com `az bicep build-params` e valores fictícios (a seção 10 já o listava, e a pendência 4.3 pedia os valores). Compila o `main.bicepparam` e, por ele, todos os módulos.
- **`infra/pipeline/setup-oidc.ps1`:** o bootstrap da identidade, idempotente. Lê os GUIDs dos papéis por nome (`az role definition list --name`), porque na 4.2 um GUID copiado estava errado.

## `deploy.yml`, passo a passo

```yaml
on:
  push:
    branches: [main]
    paths-ignore: ['docs/**', '**/*.md']
```

- A linha do registro de sessões vai direto para `main` (regra do `CLAUDE.md`); sem o `paths-ignore`, cada uma faria um deploy inteiro sem mudar nada.

```yaml
permissions:
  contents: read
  id-token: write   # pedir o token OIDC
  packages: write   # push no GHCR com o GITHUB_TOKEN
concurrency:
  group: deploy
  cancel-in-progress: false
```

- `cancel-in-progress: false`: um push novo espera o deploy em andamento, em vez de cortá-lo no meio da migração.

**1. Imagens.** `docker login ghcr.io` com o `GITHUB_TOKEN` do próprio workflow (vale só durante a execução; não é um secret guardado), e `docker build` mais `docker push` das três, com a tag igual ao SHA completo do commit. `${app^}` transforma `api` em `Api` para achar `src/Payments.Api/Dockerfile`.

**2. Login.** `azure/login@v2` com os três IDs das variáveis.

**3. Tags em uso e admin do SQL.**

```bash
revision=$(az containerapp list -g "$RESOURCE_GROUP" --query "[?name=='$name'].properties.latestReadyRevisionName" -o tsv)
image=$(az containerapp revision show -g "$RESOURCE_GROUP" -n "$name" --revision "$revision" --query "properties.template.containers[0].image" -o tsv)
tag="${image##*:}"                                       # o que vem depois do último ':'
echo "${app^^}_IMAGE_TAG=${tag:-$IMAGE_TAG}" >> "$GITHUB_ENV"
```

- `list` com filtro, não `show`: um app que não existe devolve vazio, e vazio quer dizer primeiro deploy, que usa a tag nova (seção 10). Com `show || true`, um erro de login também viraria "primeiro deploy".
- A imagem vem da **última revisão pronta** (`latestReadyRevisionName`), não do template do app. Um `update` que falhou deixa a imagem ruim no template enquanto a revisão antiga segue servindo; ler o template faria o deploy seguinte repetir a imagem ruim. Achado da revisão de código.
- Os nomes vêm de `API_APP` e `WORKER_APP` (o `env` do workflow), e `${name##*-}` tira `api` ou `worker` do nome. Se a consulta usasse nomes escritos de novo e eles divergissem, voltaria vazio, e o "primeiro deploy" poria o código novo antes da migração.
- O admin do SQL é lido do servidor (`az sql server ad-admin list`) e o e-mail é mascarado com `::add-mask::` antes de qualquer saída. Ver "O que deu errado" para o porquê de não guardar em variável.

**4. `what-if`.** Só registra a diferença no log (seção 10); o PR é a revisão.

**5. Deploy do Bicep**, com `--output none` porque a saída do `az deployment group create` imprime os parâmetros, o e-mail incluído. Nome `deploy-<sha>`.

**6. Migração.** `az containerapp job start` devolve o nome da execução, e o passo consulta `job execution show` a cada 10 s até `Succeeded`; qualquer status fora de `Running`/`Processing` falha o workflow, e a API e o worker não mudam. Um erro da própria consulta (a execução ainda não visível logo depois do `start`, um 5xx) conta como status vazio e é consultado de novo (`|| true`), porque o shell do Actions é `bash -e` e sairia no primeiro erro. `timeout-minutes: 12` fica acima do `replicaTimeout` de 600 s do job.

**7. API e worker.** `az containerapp update --image <registro>-api:<sha> --revision-suffix sha-<7>-<tentativa>`, depois o mesmo no worker, e lista as revisões ativas no log. O sufixo é curto porque o nome da revisão tem limite e precisa começar com letra. A tentativa (`GITHUB_RUN_ATTEMPT`) entrou depois da revisão de código: sem ela, reexecutar o mesmo commit pediria um nome de revisão que já existe, e reexecutar é o jeito documentado de forçar um deploy. O ensaio rodou antes dessa mudança, por isso as revisões dele são `sha-3cd86a6`.

### O banco pausado e a migração

O banco estava `Paused` às 01:08, mas a migração (01:12:54 a 01:12:57) conectou de primeira, sem retry. O Activity Log mostra por quê: o próprio deploy do Bicep gravou o banco (`sql.bicep`) e o acordou.

```text
01:10:39  Update SQL database  Started    975cc396-... (o pipeline)
01:11:26  Update SQL database  Succeeded  13c27879-... (a plataforma: retomada)
01:11:42  Update SQL database  Succeeded  975cc396-...
```

Então, na ordem do pipeline, o banco já está acordado cerca de 1 min antes da migração, e o retry do migrator fica como rede de segurança (por exemplo, se o banco pausar entre o deploy e o job, o que exige 60 min parado). A retomada levou cerca de 46 s, número que foi para a pendência do banco pausado na revisão do M4.

Teste local do retry: com o SQL Server do compose pausado (`docker compose pause sqlserver`) por 25 s, o migrator terminou em 26 s com `No migrations were applied`. Não houve retry, porque um container pausado ainda aceita a conexão TCP e ela só espera. O teste prova que `MigrateAsync` roda com a estratégia de retry ligada, mas não que o retry age.

## O que deu errado e como foi resolvido

- **Subject do OIDC em outro formato.** O primeiro login falhou:

  ```text
  AADSTS700213: No matching federated identity record found for presented assertion subject
  'repo:milsucruz@103121417/payment-webhook-processor@1414394226:ref:refs/heads/infra/deploy-pipeline'
  ```

  O repositório usa o subject imutável do GitHub (`use_immutable_subject: true`, o padrão atual), com os IDs numéricos do dono e do repositório. A credencial foi refeita nesse formato, mais seguro: um repositório recriado com o mesmo nome não herda o acesso. O script lê o prefixo de `gh api repos/<repo>/actions/oidc/customization/sub` em vez de fixar os números.
- **`SQL_ADMIN_OBJECT_ID` vazio.** `read -r login sid <<< "$(az ... --query "[0].[login, sid]" -o tsv)"` leu só o login: em `tsv`, uma lista projetada sai um valor por linha. O Bicep falhou com `InvalidExternalAdministratorSid` antes de mudar qualquer coisa. Voltei para duas consultas separadas.
- **E-mail do admin em log público.** O plano guardava `SQL_ADMIN_LOGIN` como variável do GitHub. Com o repositório público, o cabeçalho de cada passo no log mostra o script com as expressões já substituídas e o bloco `env:` com os valores, antes de qualquer máscara. O pipeline passou a ler o admin do servidor e mascará-lo; no log aparece `SQL_ADMIN_LOGIN: ***`.
- **O classificador recusou** criar o app registration e os papéis, o commit do trigger temporário e o push. O autor rodou esses passos.

## Armadilhas que ficam

- O pipeline não cria o servidor SQL do zero: ele lê o admin de um servidor que já existe. O primeiro deploy de um ambiente novo é manual (comando do `CLAUDE.md`), seguido de `infra/sql/create-users.ps1` e `infra/pipeline/setup-oidc.ps1`.
- Recriar o grupo de recursos apaga as duas atribuições do pipeline; rode o `setup-oidc.ps1` de novo.
- Um papel novo no Bicep, fora dos três da condição, faz o deploy falhar com `AuthorizationFailed` até a condição e a seção 8 mudarem.
- Um push que só muda `docs/` ou arquivos `.md` não faz deploy; para forçar, reexecute a última execução no GitHub.
