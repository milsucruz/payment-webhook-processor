## `infra/containerapps.bicep`, trecho a trecho

- **`workspace ... existing` e `listKeys()`:** o environment envia o stdout dos containers ao workspace da 4.4. A plataforma só aceita o destino `log-analytics` com `customerId` e a chave compartilhada do workspace; a chave é lida em tempo de deploy e não aparece no repositório. É a ligação da própria plataforma, não um acesso da aplicação, mas a seção 8 diz "nenhuma chave"; ficou em `docs/pending.md` (M4 review).
- **`identity` com `userAssignedIdentities`:** cada app e o job usam a identidade criada na 4.2. O Bicep recebe o ID do recurso (`apiId`, `workerId`, `migratorId`, outputs novos de `identity.bicep`).
- **`secrets` com `keyVaultUrl` e `identity`:** a API declara `stripe-webhook-secret` e `admin-api-key` como referências (`${vaultUri}secrets/<nome>`, sem versão, para usar a mais recente). O valor nunca passa pelo Bicep. As variáveis `Stripe__WebhookSecret` e `Admin__ApiKey` usam `secretRef`.
- **`ingress`:** `external: true`, `targetPort: 8080` (porta padrão das imagens ASP.NET Core) e `allowInsecure: false`, então HTTP é redirecionado a HTTPS. Worker e job não têm ingress.
- **`scale`:** API 0 a 1, worker 0 a 3 (seção 10), sem regra nenhuma por enquanto: a regra de fila e as sondas são da 4.7. Sem regra e com mínimo zero, o worker fica parado, o que é o desejado até a 4.6.
- **`resources`:** `cpu: json('0.25')` e `memory: '0.5Gi'`; Bicep não aceita decimal literal, como no SQL e no teto do Log Analytics.
- **`ServiceBus__EventsQueueName`:** o nome da fila vem de `appsettings.Development.json` localmente; em `Production` esse arquivo não é lido, então vai por variável.
- **`ServiceBus__ConnectionString` (marcador):** a validação de inicialização exige o valor, e o namespace tem chave desligada, então não há connection string real. O valor `placeholder` só deixa a API subir; publicar de fato falharia. A 4.6 troca por identidade.
- **`FaultInjection__Enabled`:** parâmetro `faultInjectionEnabled`, `true`. A conta é um sandbox do Stripe e o critério da 5.7 precisa da falha de demonstração na nuvem.
- **Job:** `triggerType: 'Manual'`, `replicaTimeout: 600`, `replicaRetryLimit: 0`. Sem tentativas automáticas, porque uma migração com falha deve ser lida, não repetida em silêncio. Ainda sem `ConnectionStrings__Payments` (4.6) e nunca disparado nesta tarefa.
- **`main.bicepparam`:** `imageRegistry` fixo, `imageTag` vem de `IMAGE_TAG` (padrão `manual`), `faultInjectionEnabled = true`.

## Comandos rodados

Provider não registrado (mesmo problema das tarefas anteriores):

```powershell
az provider register -n Microsoft.App --wait
```

Imagens: build local com os Dockerfiles do repositório, login no GHCR com o token do `gh` (escopo `write:packages`) e push. Depois, cada pacote foi tornado **público** em *Package settings*:

```powershell
gh auth refresh -h github.com -s write:packages
gh auth token | docker login ghcr.io -u milsucruz --password-stdin
docker build -f src/Payments.Api/Dockerfile -t ghcr.io/milsucruz/payment-webhook-processor-api:manual .   # idem Worker e Migrator
docker push ghcr.io/milsucruz/payment-webhook-processor-api:manual                                          # idem worker e migrator
```

Acesso anônimo conferido antes do deploy (token anônimo do GHCR e `GET /v2/.../manifests/manual`): os três responderam `200`.

```powershell
$env:SQL_ADMIN_LOGIN = "<seu UPN>"; $env:SQL_ADMIN_OBJECT_ID = "<seu object id>"
az deployment group what-if -g rg-payment-webhooks -p infra/main.bicepparam   # 4 Create: environment, API, worker, job
az deployment group create -g rg-payment-webhooks -n task-4-5 -p infra/main.bicepparam
# state Succeeded
# fqdn ca-payment-webhooks-api.delightfulocean-a8c8d259.centralus.azurecontainerapps.io
```

Os 1,5 s incluem o *cold start*: a API estava em zero réplicas e a requisição a fez subir. É a primeira medição do risco da seção 14; o `TryTimeout` de publicação (pendente da 4.7) é outra medida.

## O que deu errado e como foi resolvido

- **`Microsoft.App` não registrado:** conferido antes do deploy e registrado à mão.
- **Python não existe na máquina:** minha primeira tentativa de editar os `.bicep` com um script falhou em silêncio (só o arquivo novo foi criado). Conferi com `git status` e refiz as edições com `sed` e `cat`.
- **Primeiro `docker push` falhou com `denied`:** as camadas subiram e os três pacotes foram criados (privados, versões sem tag), mas a gravação da tag foi negada. Repetir o mesmo push funcionou. Conferido com `gh api user/packages/container/<nome>/versions`.
- **Pacotes nascem privados:** o Container Apps puxa sem credencial, então foi preciso torná-los públicos à mão antes do deploy.

## Armadilhas que ficam

- Apagar o grupo de recursos apaga o environment e os apps; recriar é rodar o Bicep. Os pacotes do GHCR não pertencem ao grupo e continuam.
- A API sobe, mas **não publica** na fila e o worker **não roda** até a 4.6: o marcador de Service Bus não tem chave válida e não há connection string do banco no worker e no job.
- Quem empurra imagens daqui em diante é o `deploy.yml` (4.8); o pipeline precisa de acesso de escrita aos três pacotes (`docs/pending.md`).
- Atrás do ingress o limitador de taxa vê o IP do proxy (`docs/pending.md`, 4.9).
- Em um ambiente recriado, a referência do Key Vault pode falhar no primeiro deploy: o role assignment da API (Secrets User) existe antes do app no Bicep, mas a propagação do RBAC no Azure leva alguns minutos. Se o app da API falhar com erro de acesso ao cofre, confira o papel com `az role assignment list` e rode o deploy de novo.
- `faultInjectionEnabled` é parâmetro do `main.bicepparam`: um evento do Stripe com `metadata[demo_fault]` falha de propósito na nuvem. Para desligar, mude para `false` e faça o deploy.
- A tag `manual` é mutável: um novo push com a mesma tag não faz uma revisão em execução baixar a imagem de novo. O `deploy.yml` (4.8) usa a tag do commit.
