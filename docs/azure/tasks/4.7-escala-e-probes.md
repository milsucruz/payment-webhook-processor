# Tarefa 4.7: regra de escala pela fila e probes de liveness e readiness

Serviços: [container-apps.md](../container-apps.md) (regra de escala, KEDA e probes, explicados lá) e [service-bus.md](../service-bus.md). Pronto quando: com a fila vazia o worker vai a zero, e o modo `flood` do simulador faz as réplicas subirem.

## Recursos criados

Nenhum recurso novo. A tarefa **muda configuração** de dois apps da 4.5 e publica três imagens.

| O quê | Onde |
| --- | --- |
| Regra `payment-events-length` no worker | `infra/containerapps.bicep` |
| Probes de liveness e readiness na API | `infra/containerapps.bicep` |
| Nome curto do namespace para a regra | `infra/main.bicep` (output `namespaceName` que já existia em `servicebus.bicep`) |
| Versão de API `Microsoft.App` de `2024-03-01` para `2025-01-01` | `infra/containerapps.bicep`, nos quatro recursos |
| Imagens `ghcr.io/milsucruz/payment-webhook-processor-{api,worker,migrator}:task-4-7` | à mão, `docker push` |

## O código, em resumo

- **`/health/ready`:** `ServiceBusQueueHealthCheck` (Infrastructure) faz um *peek* em `payment-events` com o `ServiceBusClient` da API. O `/health/live` passa a não rodar check nenhum (`Predicate = _ => false`). Detalhe em `docs/code/ServiceBusQueueHealthCheck.md`.
- **`flood [quantidade]`:** gera eventos `payment_intent.succeeded` novos, assinados, com `demo_fault=slow`, e manda direto ao webhook a no máximo 8 por segundo. Não passa pelo Stripe: não há chave de teste e gravar o `whsec_` no Key Vault é a 4.9. Detalhe em `docs/code/FloodMode.md`.
- O worker não mudou. A imagem dele ganhou a tag nova porque o `imageTag` é um só para os três apps.

## `infra/containerapps.bicep`, trecho a trecho

**Regra de escala do worker:**

```bicep
rules: [
  {
    name: 'payment-events-length'
    custom: {
      type: 'azure-servicebus'          // o scaler do KEDA para Service Bus
      metadata: {
        namespace: serviceBusNamespaceName  // nome curto (sb-...), não o FQDN
        queueName: 'payment-events'
        messageCount: '20'              // alvo por réplica: ceil(ativas / 20)
      }
      identity: workerIdentityId        // resource ID da identidade user-assigned do worker
    }
  }
]
```

- `minReplicas: 0` e `maxReplicas: 3` já existiam (4.5). O intervalo de leitura (30 s) e o *cooldown* (300 s) ficaram no padrão: a arquitetura não pede outros valores e o padrão atende o "pronto quando".
- `identity` em vez de `auth`: sem connection string e sem segredo, como manda a seção 8.

**Probes da API:**

```bicep
probes: [
  { type: 'Liveness',  httpGet: { path: '/health/live',  port: 8080 }, periodSeconds: 10, timeoutSeconds: 3,  failureThreshold: 3 }
  { type: 'Readiness', httpGet: { path: '/health/ready', port: 8080 }, initialDelaySeconds: 1, periodSeconds: 5, timeoutSeconds: 10, failureThreshold: 3 }
]
```

- Liveness: o endpoint só confirma que o processo responde, então 3 s de timeout sobram.
- Readiness: 10 s de timeout porque o *peek* usa as tentativas do cliente da API (2 retries, `TryTimeout` de 2 s, cerca de 8 s no pior caso). Período curto (5 s) para a réplica nova entrar no tráfego logo no *cold start*.
- Sem *startup probe*: a plataforma mantém a padrão (TCP na porta do ingress).
- O worker não tem probes: sem ingress e sem servidor HTTP.

## Comandos rodados

`az bicep build` com a versão antiga avisou que `identity` não existe na regra:

```text
Warning BCP037: The property "identity" is not allowed on objects of type "CustomScaleRule". Permissible properties include "auth".
```

Com `2025-01-01`, o build saiu limpo. O `what-if` mostrou a regra nova no worker e os containers mudando; o resto foi o ruído já conhecido (item 4.2 de `docs/pending.md`) e campos que a plataforma preenche (`workloadProfileName`, `exposedPort`, `cooldownPeriod`) aparecendo como removidos.

Imagens e deploy, por um script rodado pelo autor (o classificador de permissões bloqueia o `docker push`):

```bash
docker push ghcr.io/milsucruz/payment-webhook-processor-api:task-4-7     # idem worker e migrator
IMAGE_TAG=task-4-7 az deployment group create -g rg-payment-webhooks -n task-4-7 -p infra/main.bicepparam
# Succeeded
```

Leitura de volta: o worker tem `rules[0].custom.identity` = `id-payment-webhooks-worker` e a API tem as duas probes.

- A ativação de 0 para 1 veio das 2 mensagens do teste de *cold start*; o `flood` levou a 3 (o máximo; `ceil(96/20) = 5`).
- 100 envios em 30 s, todos `200`: nenhum `429`, o ritmo de 8 por segundo ficou abaixo do limite de 100 a cada 10 s.
- A fila esvaziou em cerca de 1,5 min (3 réplicas × 4 chamadas ÷ 10 s do `slow`), e o worker voltou a zero cerca de 5 min depois.

No banco, com `sqlcmd` e `az login`:

```text

flood inbox=100
coldstart inbox=1      # o mesmo evento foi enviado duas vezes: uma linha só
```

## O que deu errado e como foi resolvido

- **`identity` na regra ignorada na `2024-03-01`:** o `BCP037` avisou no build; subi a versão dos quatro recursos `Microsoft.App` para `2025-01-01`, para não misturar versões.
- **O risco do papel do KEDA (seção 14) não aconteceu:** a documentação do KEDA pede *Manage* com connection string, mas com a identidade gerenciada o Data Receiver bastou. O log `triggered by s0-azure-servicebus-payment-events` e a subida para 3 réplicas provam a leitura. A seção 8 não mudou, e o pipeline não precisa de papel novo.
- **`--type system` dos logs só aceita JSON**, e `az monitor log-analytics query` pede uma extensão. Usei `az rest` na API do Log Analytics (`https://api.loganalytics.io/v1/workspaces/<id>/query`).
- **`length(@)` no `--query` quebra no `az.cmd` do Windows** (parênteses). Contei as linhas de `[].name`.
- **Ler o segredo do Key Vault:** o classificador recusou guardá-lo numa variável de ambiente persistente. O script de verificação, rodado pelo autor, lê o segredo para uma variável do próprio processo.

## Armadilhas que ficam

- Uma mensagem ativa parada na fila mantém 1 réplica do worker de pé; a dead-letter não conta.
- O cold start da API passa de 20 s quando a plataforma precisa baixar a imagem num nó novo.
- Mudar a regra ou as probes cria uma revisão nova; a revisão sobe com 1 réplica e só volta a zero depois do *cooldown*.
