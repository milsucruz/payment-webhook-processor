## O código, em resumo

### `infra/stripe/register-webhook.ps1`

```powershell
$fqdn = az containerapp show -g $ResourceGroup -n $ApiName --query properties.configuration.ingress.fqdn -o tsv
$url = "https://$fqdn/webhooks/stripe"
```

A URL sai do Azure, não de um parâmetro: se o ambiente for recriado, o FQDN muda e o script continua certo.

```powershell
$existing = (stripe webhook_endpoints list -d limit=100 | ConvertFrom-Json).data | Where-Object { $_.url -eq $url }
if ($existing) { throw "..." }
```

O Stripe só devolve o segredo (`whsec_`) na criação do endpoint. Se já existe um para a mesma URL, não há como gravar o segredo dele de novo, e criar outro faria o Stripe entregar cada evento duas vezes, uma assinada com cada segredo, com metade rejeitada. Por isso o script para e diz como apagar.

```powershell
$arguments = @('-d', "url=$url", '-d', "api_version=$ApiVersion", ...)
$events | ForEach-Object { $arguments += @('-d', "enabled_events[]=$_") }
$endpoint = stripe webhook_endpoints create @arguments | ConvertFrom-Json
```

- **Stripe CLI, não a API com `sk_test_`:** o CLI já está logado no sandbox com a própria chave, e essa chave pode criar endpoints. Nenhuma chave nova precisou ser criada ou guardada.
- **Os 7 eventos da seção 2:** o Stripe recomenda assinar só o que a integração usa.
- **`api_version` fixa em `2026-09-30.endive`:** sem ela o endpoint segue a versão padrão da conta, e uma atualização no Dashboard mudaria o JSON sem aviso. O parser e as fixtures foram escritos para essa versão.

```powershell
$secretFile = New-TemporaryFile
try {
    Set-Content -Path $secretFile -Value $endpoint.secret -NoNewline -Encoding utf8NoBOM
    az keyvault secret set --vault-name $vaultName -n stripe-webhook-secret --file $secretFile --encoding utf-8 -o none
    az containerapp secret set ... --secrets "stripe-webhook-secret=keyvaultref:${vaultUri}secrets/stripe-webhook-secret,identityref:$identity"
    az containerapp revision restart -g $ResourceGroup -n $ApiName --revision $revision | Out-Null
} catch {
    stripe webhook_endpoints delete $endpoint.id --confirm | Out-Null
    throw
} finally {
    Remove-Item $secretFile
}
```

- **Arquivo temporário:** o segredo vai para o cofre por um arquivo, não como argumento (`--value`), que fica visível na lista de processos enquanto o `az` roda. `-NoNewline` evita gravar uma quebra de linha junto com o segredo, e o `finally` apaga o arquivo mesmo em caso de erro. O segredo nunca é impresso.
- **Desfazer se falhar:** cofre, URI, identidade e revisão são lidos **antes** de criar o endpoint, então um grupo sem cofre ou sem identidade falha sem tocar no Stripe. Se algo falhar depois da criação, o `catch` apaga o endpoint novo, porque o segredo dele não poderia ser lido de novo, e rodar o script outra vez funciona. Esse ajuste veio do code review; a versão rodada na tarefa não o tinha.

- **`az containerapp secret set`:** regrava a mesma referência, sem mudar nada em relação ao Bicep, só para forçar a releitura do cofre (ver "O que deu errado"). O restart, em seguida, faz a variável `Stripe__WebhookSecret` pegar o valor novo.

### Forwarded headers na API (`src/Payments.Api/Program.cs`)

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor;
    options.ForwardLimit = 1;
    options.KnownIPNetworks.Clear();
    options.KnownProxies.Clear();
});
...
app.UseForwardedHeaders();
app.UseRouting();
app.UseRateLimiter();
```

Atrás do ingress, `RemoteIpAddress` é sempre o IP do proxy, então o limite por IP da 3.6 virava um balde único: um flood de qualquer origem fazia o Stripe receber `429`.

- **Só o último valor (`ForwardLimit = 1`):** o ingress acrescenta o IP de quem chamou no fim do `X-Forwarded-For`. O que vem antes foi escrito pelo próprio cliente e pode ser falso.
- **Listas de proxies vazias:** por padrão o middleware só confia em `127.0.0.1`, e o IP do Envoy do ingress não é fixo. Confiar em qualquer origem é seguro porque o container só é alcançável pelo ingress. Deixaria de ser se a API fosse exposta por outro caminho.
- **Antes de `UseRouting`:** precisa trocar o IP antes de o rate limiter particionar.
- **Sem `X-Forwarded-Proto`:** nada na API gera URL ou redireciona para HTTPS.
- **Descartado:** a allowlist de IPs do Stripe (seção 8), que exige manter a lista.

Testes novos em `StripeWebhooksControllerTests`: `Each_forwarded_client_ip_has_its_own_rate_limit` e `A_forged_forwarded_ip_does_not_get_a_new_rate_limit`. Com `ForwardLimit = 2`, o segundo falha.

### Cold start contra o Stripe

Com a API em zero réplicas (00:36:58), `stripe trigger` às 00:37:07:

| Momento | O que aconteceu |
| --- | --- |
| 00:37:09 | Réplica criada (o pedido do Stripe acordou a API) |
| 00:37:26 | `Now listening on: http://[::]:8080` |
| 00:38:19 | `payment_intent.created` gravado no inbox |
| 00:38:51 | `payment_intent.succeeded` ainda com `pending_webhooks: 1` |

O Stripe não esperou o cold start para um dos dois eventos. Nas entregas das 22:45, que também caíram numa réplica recém-criada, o reenvio do Stripe chegou por volta de 23:43, cerca de 1 h depois. Decisão: a réplica mínima continua em zero. Uma réplica de 0,25 vCPU e 0,5 GiB ligada o mês todo custaria cerca de US$ 4 depois da cota gratuita, quase todo o orçamento de US$ 5, e nada se perde, porque o evento rejeitado não entra na fila e o Stripe reenvia. Antes de uma demo, um `curl https://<fqdn>/health/live` aquece a API.

## O que deu errado e como foi resolvido

- **A API subiu com o segredo antigo.** O primeiro script reiniciava a revisão logo depois do `az keyvault secret set`, e a réplica nova recebeu o *placeholder*: às 22:39:09 o log mostrou `Rejected Stripe webhook: The expected signature was not found`, e o ingress contou 4 × `400`. O Key Vault já tinha a versão nova (22:38:22). O Container Apps guarda o valor lido do cofre e só o relê sozinho em até cerca de 30 min. Resolvido regravando a referência com `az containerapp secret set` e reiniciando de novo, e o script passou a fazer isso.
- **Um espaço colado quebrou a referência.** Ao rodar o `secret set` à mão, o terminal partiu a linha em `identit yref`. O CLI não reconheceu o formato e gravou o texto inteiro como valor literal: `az containerapp show` passou a listar o segredo sem `keyVaultUrl`. Corrigido rodando o comando de um arquivo `.ps1`, sem colagem longa. O restart ainda não tinha sido feito, então a API nunca usou o valor quebrado.
- **O deploy da imagem foi bloqueado no agente.** O modo automático do Claude Code não deixou o agente publicar a imagem nem gravar segredos; o autor rodou esses comandos com `!`.

## Armadilhas que ficam

- **Rotação do segredo:** gravar no cofre não basta. É preciso regravar a referência e reiniciar a revisão, ou esperar a releitura de até 30 min.
- **Tudo do sandbox vai para a nuvem:** o `stripe trigger` local também é entregue ao endpoint e acorda API, worker e banco. Para parar: `stripe webhook_endpoints update <we_...> -d disabled=true`.
- **Recriar o ambiente:** muda o FQDN. Apague o endpoint antigo e rode o script de novo.
- **Primeiro evento depois de um tempo parado:** pode chegar só no reenvio do Stripe, cerca de 1 h depois. Aqueça a API antes de uma demo.
