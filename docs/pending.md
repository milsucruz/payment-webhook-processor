| 3.4 | `ServiceBusDeadLetterQueue.ReprocessAsync` locks every dead-lettered message it receives before the match and abandons them afterwards. With many messages in the dead-letter, a reprocess holds them all locked while it searches, and a concurrent reprocess of one of them answers `404` until the locks are released. The docs say an abandon raises `DeliveryCount`, but in the emulator the other messages kept `DeliveryCount` 5 after two reprocess calls. Task 3.5 found how the emulator counts: a peek returns the number of deliveries that ended without a settlement (0 for a message dead-lettered by the worker on its first delivery, 5 for `MaxDeliveryCountExceeded`), while a receive returns that number plus one, since it is a new delivery; this is what `GET /api/dead-letters` shows. Check both against the real namespace, together with the delivery-counting risk in section 14: the count after an abandon in the dead-letter, and the time a reprocess takes with about 100 messages there. The M4 review moved it to the dead-letter screen, which shows `DeliveryCount` and will have cloud dead-letters to check against. | 5.5 |
